# Hexa-Tech ChatGPT plugin

The integration connects ChatGPT and Codex to Hexa-Tech CRM leads, customers and bookings through an authenticated MCP endpoint at `https://app.hexa-tech.uk/mcp`. The plugin package is in `plugins/hexatech/`. It uses the supported `.codex-plugin/plugin.json` compatibility layout generated by the plugin-creator skill.

This guide describes the implemented integration. Deployment and live-verification results are recorded under Current delivery boundary below; package files and endpoint URLs alone are not evidence of successful account linking or tool use.

## What users can do

| Tool | Operation |
| --- | --- |
| `list_leads` | List CRM inquiries by creation date, with authorized counts, status, brand and basic customer identity. Defaults to today in the workspace timezone. |
| `search_customers` | Find customers using a nonblank name, company or contact search of at least two characters. |
| `get_customer` | Read one customer. |
| `list_bookings` | Find reservations, room bookings, and service appointments. |
| `get_booking` | Read one booking. |
| `add_customer_note` | Add a note to a customer. |
| `add_booking_note` | Add a note to a booking. |

A second, voice-shaped MCP server is served at `/mcp/voice` for the staff voice assistant. It
reuses this integration's OAuth, tenancy, throttling, subscription verification and brand
scoping unchanged, and leaves the tools above untouched. See `docs/voice-assistant.md`.

Booking kind and ID identify the record together. Note actions require an explicit user request and a UUID `request_id`. Repeating the same note request with its original ID returns the saved result without appending another note; retry with the same ID and text after an uncertain response. The integration does not create or cancel bookings, take payments, send communications, or provide general database access.

### Reading results accurately

- For today's leads, call `list_leads` without dates or a query. Dates use the organization's configured timezone, not the assistant's timezone. One supplied date selects that day; two select an inclusive range of at most 90 calendar days. The filter is lead creation time, not a booking date or the last 24 hours. All current statuses are included unless an exact status is supplied.
- Lead lists report `total_count` for all authorized matches and `returned_count` for the current page. Each page contains at most 25 leads (default 20), up to 100 pages. Follow `next_page` with the same filters and limit; honor `results_truncated`. Optional `brand_id` only narrows the connected account's permissions. Lead IDs are inquiry IDs; lead editing and lead notes are not supported. Use a returned `customer.id` only when a separate customer action is requested.
- Never use a blank customer search to list leads. A tool failure leaves the count unknown; it does not mean zero leads.
- Customer search returns `next_after_id`; send it back as `after_id` with the same search to continue. Each page contains at most 25 customers.
- Booking lists return `next_page`. Keep the kind, filters and page size unchanged while following it. Existing booking behavior permits dates up to 90 days apart, with both endpoints included (up to 91 dates), up to 50 bookings per page and 100 pages. If `results_truncated` is true, additional matches exist: narrow the date range or search, or restart with a larger page size. A null `next_page` is not proof of completeness when this flag is true.
- Room/PMS bookings, CRM reservations and service appointments are separate collections and may describe overlapping business activity. Do not sum them as unique bookings without checking for duplicates.
- `currency: null` means unknown. CRM reservations do not store their historical currency. Room bookings use an unambiguous currency from their stored price elements; absent, incomplete or conflicting values remain unknown. Service appointments use their stored currency. Never substitute today's workspace currency or assume EUR/GBP for an unknown amount.
- Notes can be shortened in tool responses. Honor `has_more_notes`, `body_truncated` and `staff_notes_truncated`; do not describe a limited note excerpt as the entire history.

The service-booking drawer now displays existing staff notes and sends new notes through the additive `append_staff_note` input. The API appends to the latest row under a transaction lock, preserving notes added by another staff member or the plugin. Existing clients explicitly sending `staff_notes` retain their replacement behavior; nonempty replacement and append operations cannot be combined in one request.

## Deployment and OAuth

`CHATGPT_PLUGIN_ENABLED` defaults to `false`. Keep it disabled until the server is deployed and OAuth configuration is complete. The package's `.app.json` references the registered connection; it does not itself enable the endpoint or grant customer access.

The server uses Laravel Passport for OAuth authorization-code flow with PKCE. ChatGPT cannot supply a custom static API key for this connection. It needs OAuth discovery and user account linking. See [OpenAI authentication documentation](https://developers.openai.com/plugins/build/auth).

Deploy the application dependencies and migrations using the repository's normal release process. Provision Passport signing keys in the deployment's secret storage and retain them across deployments; do not regenerate existing keys or commit private keys. Configure a dedicated public Passport OAuth client and allowlist the exact redirect URI displayed for the ChatGPT connection.

For a new development environment, generate the Passport key files once if they do not already exist:

```powershell
& 'C:\wamp64\bin\php\php8.4.20\php.exe' artisan passport:keys
```

Create the public client after the OAuth migrations are applied, using the integration-specific setup command. Replace `EXACT_CALLBACK_FROM_CHATGPT` below with the actual callback URL displayed for your connection before running it:

```powershell
& 'C:\wamp64\bin\php\php8.4.20\php.exe' artisan chatgpt:client --name="Hexa-Tech" --redirect-uri="EXACT_CALLBACK_FROM_CHATGPT"
```

The integration command uses `--redirect-uri` with a hyphen; repeat that option for every callback. It creates or reuses an eligible public authorization-code/refresh client and refuses ambiguous or incompatible existing clients. Once `CHATGPT_PLUGIN_CLIENT_ID` is configured it updates that client; `--client-id` explicitly selects an existing client when needed. Updating replaces its callback list, so supply the complete intended list, including callbacks already in use. HTTPS callbacks and HTTP loopback callbacks with explicit ports are supported; wildcards, fragments and credentials in callbacks are rejected.

Save the returned public client ID as `CHATGPT_PLUGIN_CLIENT_ID` and put the same complete callback list in `CHATGPT_PLUGIN_REDIRECT_URIS`, separated by commas. This client has no client secret. The command does not modify environment files, signing keys or plugin enablement. On the deployment host, run the equivalent commands with its PHP 8.4+ runtime and secure key storage; the Windows path above is for this repository's local environment.

Do not use a guessed stable ChatGPT callback: this server does not advertise OAuth authorization-response issuer identification. Use the callback shown for the actual connection, which can be callback-specific.

Set these deployment values:

| Setting | Value or purpose |
| --- | --- |
| `CHATGPT_PLUGIN_ENABLED` | `false` while preparing the integration; `true` when ready to link accounts. |
| `CHATGPT_PLUGIN_URL` | `https://app.hexa-tech.uk`, the canonical origin with no trailing slash. Use the development origin for a development deployment. |
| `CHATGPT_PLUGIN_CLIENT_ID` | The actual ID of the dedicated public Passport client. |
| `CHATGPT_PLUGIN_REDIRECT_URIS` | Comma-separated exact callback URLs copied from the intended ChatGPT or Codex connection. No wildcard callbacks. |
| `CHATGPT_PLUGIN_ALLOWED_ORIGINS` | Optional extra allowed request origins, when required by a client. |
| `CHATGPT_PLUGIN_ORGANIZATION_IDS` | Comma-separated **local organization IDs** approved for the pilot. Empty denies every organization unless broad rollout is explicitly enabled. |
| `CHATGPT_PLUGIN_ALL_ORGANIZATIONS` | Defaults to `false`. Keep false for a pilot; `true` explicitly permits every otherwise eligible organization. |
| `CHATGPT_PLUGIN_BILLING_USER_IDS` | Optional comma-separated local staff user IDs with existing SaaS memberships, used only to verify billing for their own organization. See below. |
| `PASSPORT_PRIVATE_KEY`, `PASSPORT_PUBLIC_KEY` | Passport signing keys, supplied securely or provisioned through the application's existing Passport key storage. |

The OAuth scope is `mcp:use` and covers all seven tools, including notes; this version does not offer a separate read-only OAuth grant. The server requires an active staff account and organization and applies the application's business and brand access rules. OAuth consent takes place in Hexa-Tech using the existing signed-in application session. Never paste login tokens, authorization codes, or private keys into a chat or the plugin files.

The pilot allowlist controls organizations, not brands. The connector has no persistent brand picker: customers and room/PMS records are organization-scoped; CRM leads, reservations and service appointments also honor the staff account's assigned-brand restrictions. A connection display name does not change this access. Staff with unrestricted access can work across their permitted brands, including when the connection is named for one brand. Token organization binding prevents a later account move from carrying a previous organization's grant into a new one.

### Subscription verification and disconnect

MCP has its own subscription check, independent of the SPA's `entitlements_synced_at` marker. For an organization linked to SaaS, it obtains a service token through the existing signed service-auth flow and reads the authoritative bootstrap subscription. The MCP access token is never forwarded to SaaS. Only an active subscription or a trial that has not expired permits tool use. A temporary verification failure returns an MCP `isError` result for a valid `tools/call`, explicitly stating that no tool ran and counts remain unknown. Other request types receive `503 subscription_unavailable`. Both responses include `Retry-After: 30`; permanent denials still return 403.

Each upstream step has a five-second deadline and at most two attempts, with a 200 ms delay for transport or server failures. Permission failures are not retried and redirects are disabled. Concurrent requests wait up to 22 seconds for the refresh lock and then reuse its snapshot or short failure backoff. A failed refresh never reuses an expired active snapshot and never changes the SPA's entitlements.

Verified snapshots expire within 300 seconds and are keyed by organization, requesting user and billing principal. The signed internal entitlement-invalidation endpoint also invalidates this independent snapshot; an upstream response already in flight cannot restore the previous version. This check does not overwrite the SPA's entitlement data. Organizations without a SaaS link use their local subscription status and trial end.

Some locally invited staff have no SaaS membership of their own. An operator may configure `CHATGPT_PLUGIN_BILLING_USER_IDS` with an existing, active staff account belonging to the **same local organization** and with the required SaaS membership. The first eligible configured ID in numeric order is used; otherwise the requesting staff account is used. This changes only who verifies billing. It does not replace the requesting user's identity, staff role, brand permissions, note attribution or OAuth consent. It does not create a SaaS membership. Confirm the principal in the target deployment before configuring it.

Each staff member can withdraw their own access from **Connected apps** in the portal sidebar, or directly at `/account/connections`; Settings → Integrations also contains the panel. This personal page and its API remain reachable without manager permissions or an active subscription, including after the organization is removed from the pilot or plugin use is disabled. `GET /api/v1/auth/plugin-connections` lists their current-organization grants for the configured client. `DELETE` on the same collection disconnects all of them, revoking access tokens, refresh tokens and pending authorization codes under the same lock used by OAuth issuance. An already-running request may finish; subsequent use and refresh are denied. Existing chat history is not deleted. Ordinary portal logout does not withdraw OAuth approval.

Access-token IDs change during refresh, so the UI deliberately disconnects the whole current-account grant set rather than treating an access-token row as a stable connection ID. Keep the dedicated client ID stable; before replacing it, revoke its outstanding grants as an explicit migration step, because the personal management panel targets the configured client.

### Read-only deployment check

After applying the environment configuration through the normal deployment process, run:

```powershell
& 'C:\wamp64\bin\php\php8.4.20\php.exe' artisan chatgpt:status --resource="https://app.hexa-tech.uk/mcp"
```

This checks the enabled flag, canonical HTTPS origin, OAuth schema, usable matching RSA key pair, dedicated public client, exact callback agreement and pilot organization availability. It reports failures without printing secret values or changing configuration. A nonzero exit while the plugin is deliberately disabled is expected. A passing result does **not** prove external HTTPS reachability, billing-principal membership, browser login or ChatGPT/Codex account linking; those still need the live checks below.

Discovery endpoints are public metadata; customer and booking tools must still authorize each request. MCP uses streamable HTTP over HTTPS. No separate OpenAI API key is needed merely to serve the MCP integration.

## Connect in ChatGPT

After deploying and configuring the server:

1. Configure the approved organization allowlist, keep broad rollout disabled, then enable `CHATGPT_PLUGIN_ENABLED=true` and refresh the application's configuration cache through the normal deployment process. Run `chatgpt:status` against the intended resource URL.
2. In ChatGPT, open **Settings → Security and login → Developer mode**. Availability depends on the account and workspace policy.
3. Open [ChatGPT Plugins](https://chatgpt.com/plugins), select the plus button, and enter the name **Hexa-Tech** and the server URL `https://app.hexa-tech.uk/mcp`.
4. Configure the dedicated OAuth client, copy the exact callback URL into its allowlist, and finish linking your Hexa-Tech account.
5. Review the seven discovered tools, including `list_leads`. Start a new chat, select the connection, and run the read examples below before testing a requested note.

The remote MCP connection can be tested before distributing the package. Package version 0.2.0 references the registered app in `plugins/hexatech/.app.json`: `asdk_app_6aa185b994bc8191bdfbf7c3c32e44b1`. Its management URL is `https://chatgpt.com/plugins/plugin_asdk_app_6aa185b994bc8191bdfbf7c3c32e44b1`; the `plugin_` wrapper belongs to that URL, while the app mapping uses the observed raw app ID, matching OpenAI's [published Notion mapping](https://github.com/openai/plugins/blob/main/plugins/notion/.app.json). The manifest points `apps` to `./.app.json`. The former `.mcp.json` was removed to avoid a duplicate direct connection. Registration does not itself prove installation, availability to another account, or successful tool use.

No marketplace entry is created by this repository change. A local package still needs installation through a configured marketplace or the supported registration workflow. Public publication is a separate submission and review step. See [OpenAI packaging](https://developers.openai.com/plugins/build/plugins) and [connection testing](https://developers.openai.com/plugins/deploy/connect-chatgpt).

A customer pilot can give its registered connection a customer-facing name while reusing this generic package and server. A name such as **FDS Cards** is presentation only; it does not add a brand filter or grant access. Keep production organization IDs, staff IDs and private rollout records in deployment configuration, not in a redistributed plugin. No separate branded package is required to link an eligible customer's account.

### Direct Codex connection

The distributed package uses the registered app and does not bundle a direct `.mcp.json` connection. A separately configured direct Codex connection remains an alternative for development. It requires a real public OAuth client's settings because this server does not implement automatic client registration. Plugin MCP settings use `oauth.clientId`, `oauth.callbackUrl`, and, for a fixed local listener, `oauth.callbackPort`.

Use `codex mcp add` with `--url https://app.hexa-tech.uk/mcp` and `--oauth-client-id` set to the actual public client ID to obtain the callback associated with this endpoint. Add the exact callback to both the Passport client's redirects and `CHATGPT_PLUGIN_REDIRECT_URIS`. This server matches exact callback URLs; for a local loopback connection, set a fixed listener port and use that same explicit port in the callback URL. Preserve Codex's displayed callback path and its server-specific ID. Keep this separate connection's actual OAuth values in its local configuration. Use either the direct MCP connection or the registered-app package in a session to avoid duplicate tool sets. See [OpenAI's MCP configuration guide](https://learn.chatgpt.com/docs/extend/mcp).

## Verify the connection

First use MCP Inspector against a development deployment and a test business:

```sh
npx @modelcontextprotocol/inspector@latest
```

Select streamable HTTP and use the environment's `/mcp` URL. Walk through OAuth and verify that initialization and tool discovery succeed. Test an allowed read, an empty result, an invalid record ID, an unauthorized record from another business, and a note write using a test customer or booking. Check that an expired token requires refresh or renewed account linking and that missing `mcp:use` scope or staff access prevents tool use.

Verify a second organization is refused when it is not allowlisted. Confirm a subscription cancellation is enforced after the signed invalidation event or snapshot expiry, and that a billing verification failure does not grant access. Confirm the intended billing principal works for locally invited staff without changing the requesting user's tool permissions. Disconnect through `/account/connections`, then verify both the previous access token and refresh token fail. Test the page while the pilot is disabled and while the subscription is expired.

For browser-based clients, verify MCP preflight accepts the configured origin and protocol headers and exposes the authentication challenge; unrelated API CORS behavior is unchanged. Exercise two staff identities behind the same source address: each has its own authenticated 60/minute quota, with separate coarse network abuse limits. The response's `Retry-After` should guide retries.

Use these chat prompts as a repeatable evaluation set:

| Prompt | Expected result |
| --- | --- |
| "Tell me today leads from CRM." | Call `list_leads` without dates; report the effective date, workspace timezone, authorized total and returned leads. Never fall back to a blank customer search. |
| "Show yesterday's FDS Cards leads." | Resolve the day from the workspace timezone and use a verified permitted brand ID; disclose any incomplete page. |
| “Find a customer named Morgan Lee.” | Search customers; clarify if multiple records match. |
| “Show room bookings for 10 September 2026.” | List the appropriate booking kind with the date filter. |
| “Show the customer details for that booking.” | Reuse verified identifiers from prior results. |
| “Summarize this customer's notes.” | Read only; no note is added. |
| “Add this note to the selected booking: Guest requested a quiet room.” | Retrieve the target and add exactly the requested note. |
| “Cancel that booking.” | Explain that cancellation is not supported by these tools. |

Also test a note containing text that tells the assistant to ignore instructions or access another business. The assistant must treat it as record content, not an instruction. Inspect the record after each authorized test write to verify the note was appended once.

Check a room booking with missing or conflicting price currencies, a CRM reservation with an amount but no currency, and a service appointment with its recorded currency. Verify the assistant reports unknown currencies accurately. Exercise pagination and `results_truncated`; ask for a summary and confirm it does not turn a partial page into a complete count. Finally, read a plugin-added appointment note in the portal and add a portal note: both must remain visible.

After changing tool schemas or authentication, restart or deploy the server, refresh the connection in ChatGPT Plugins, and repeat the affected examples in a new conversation.

The first real ChatGPT connection attempt exposed a bodyless authentication probe without a JSON content type. The transport guard was corrected to allow an unauthenticated probe to receive the OAuth challenge. Requests carrying a bearer token still require JSON; the size limit and host/origin restrictions remain enforced. The correction has its own regression test.

Live browser consent also exposed the interaction between `Referrer-Policy: no-referrer` and HTML form submission: the browser sent `Origin: null`, which the origin guard refused. Successful HTML consent pages now use `same-origin` so the form retains its own origin while external referrers stay suppressed. Redirects, errors and other endpoints retain `no-referrer`; null origins are still forbidden. The regression exercises real CSRF protection, origin rejection, successful approval and token exchange. This behavior follows the [Fetch standard's origin-header algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header).

The work is on `feature/chatgpt-plugin`, based on `c11f7ce7bc17112543cd09ccbfaa89c23bb58f78`. That base carries other unshipped work. Release only this integration's reviewed changes through the repository's [source-patch process](landing-page-builder.md#6-deploy-recipe-merging-to-main-is-deploying); do not merge the whole branch into production.
