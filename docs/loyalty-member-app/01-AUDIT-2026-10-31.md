# Members' app audit: "Hotel Loyalty" (Expo), 2026-10-31

This was a read-only audit. No files were changed and no git writes were made. The app repository is `/home/user/hotel-tech-loyalty-mobile`.
It is a shallow clone with one visible commit, `c3deea3` from 2026-08-20 ("Make Android push fixable"). `node_modules` is not installed,
so the versions below come from `package-lock.json`, and `tsc` was not run. Size: 59 TS/TSX files, 11,636 lines. For comparison, the staff
app has 50 files and 5,263 lines, and the portal has 8,593 lines (not counting tests).

- **SDK 54 is the last SDK that allows the legacy architecture.** Any upgrade turns on the New Architecture. That is the same Fabric/iOS 18

- **API host.** `lib/api.ts:4` reads `EXPO_PUBLIC_API_URL`, with `https://loyalty.hotel-tech.ai/api` as the fallback. Every `eas.json` profile and the
  committed `.env` set that host, which is the hotel sub-brand host (`frontend/src/lib/industryHosts.ts:75`). The staff app uses `app.hexa-tech.uk`.

  `components/ui/WidgetWebView.tsx:24` and `app/settings.tsx:378,388`.

  Member emails are unique across all organisations (`Rule::unique('users','email')->where('user_type','member')`). When one email and password
  match two accounts, login refuses ("More than one account matches"). The app has no way to choose or switch venue. Each venue's branding
  arrives at run time from `GET /v1/theme` (`app/_layout.tsx`).
- **EAS and store identity.**

  - iOS and Android bundle id `com.hotelloyalty.app`; App Store Connect app `6765608479`; team `HNWSAQ5CQ9`.
  - iOS build 17 (v1.2.0); Android versionCode 8. `appVersionSource: remote`.

**Every path the app calls still exists** in `routes/api.php` (lines 112-187 and 346-414). Existing member endpoints the app never calls:
`GET member/chat`, `GET member/benefits`, `POST member/benefits/{id}/request`, `DELETE member/benefits/requests/{id}`, `GET member/stamps`,

**What the portal and API offer that the app lacks** (portal: `frontend/src/portal/PortalApp.tsx` routes; API: `member/portal/*`, `routes/api.php:417-458`):

1. **The startup call** (`GET member/portal`). It carries:
   - venue capabilities: loyalty, services, stays, chat, events, payments and the Stripe publishable key;
   - cancellation policies and check-in/check-out times;
   - the venue's currency and time zone;
   - the member's `notification_preferences` and `sms_consent`;
   - **membership validity** (`member.membership.valid_until` and its state).
2. **Native booking.** Stays and appointments with member prices, coupons (`coupons/resolve`), Stripe payment intents, confirm, and the bank-redirect
   return (`payments/{pi}`). The app instead opens the public widget, which books as an anonymous guest. There is no member price and no coupon,
   and points come only through `certainMemberForStay` at award time.
3. **Real bookings, with self-cancellation** (`portal/bookings`, `bookings/{kind}/{id}`, `…/cancel`).
4. **Tier benefits and benefit requests.** `docs/loyalty-workspace.md:730` and the staff app's README (acceptance step 11) both assume
   "the member app" sends these; it does not.
5. **Stamps and credit** (Release 7). `docs/loyalty-workspace.md:791` notes they are missing "until their next build".
6. **Events**, with sign-up and cancel (Release 8).
7. **Help.** The portal's per-industry help in five languages, against a hard-coded hotel FAQ.
8. **Language.** The portal has a language picker and five-locale bundles; the app has neither.
9. **Consent switches.** The app has no marketing-consent or SMS-consent switch.
10. **Calendar.** No `.ics` export.

Features the app has and the portal does not: push notifications, the in-app QR join scanner, the review form, the biometric lock, screen
brightness raised for the QR code, and in-app chat.

**App calls whose answers changed meaning or shape**

- **Bookings.** `member/bookings` reads `LoyaltyMember::bookings()` → `App\Models\Booking`, the legacy `bookings` table. Nothing under `app/`
  writes that table (grep). Real bookings live in `booking_mirror` and `service_bookings`, which the portal reads through `MemberBookingQuery`.
  So Bookings and Booking detail effectively show nothing current.
- **Tier progress.** `progress.points_needed` holds the programme's own measure; `progress.by` is points, visits or spend
  (`LoyaltyService::summaryProgress`, line 1377). The app always writes "N points to Gold" (`(tabs)/card.tsx:282`), as
  `docs/loyalty-workspace.md:800` admits.
- **Inbox taps.** A tap reads a top-level `item.action_url` (`notifications.tsx:115`). The rows are `push_notifications` records with a `data`
  JSON column and no `action_url` column, so the tap does nothing.
- **Push taps.** The app routes only `type` `review_request` and `offer` (`useNotifications.ts`). The server sends `points_earned`, `tier_upgrade`,
  `tier_downgrade`, `new_offer` (with an empty `data`), `birthday`, `reward_nudge` and `campaign` (`NotificationService.php`,
  `SendNotificationCampaignChunk.php:220`). A tap therefore opens no screen.
- **Tier colours and card metals** come from the tier's *name* (Bronze, Silver, Gold, Platinum, Diamond in `constants/tiers.ts` and
  `LoyaltyCard.tsx` `METAL`), not from `tier.color_hex`. A venue's custom tier names fall back to Bronze.
- **Sign-up form.** `public/join` now carries `referrals:false` and `theme`. The app ignores both and always offers the referral-code field.

## 3. Quality

- **TypeScript.** `strict` is on, but there are 128 `any` annotations (72 of them `as any`), many on route pushes and API configs. Answers are
  untyped `r.data`. CI runs `tsc --noEmit` (`release.yml`). There is no ESLint.
- **Tests.** There are none: 0 test files. The staff app has vitest and a locale-parity test; the portal has 45 test files.
- **Error handling.** The axios client (`lib/api.ts`) has:
  - a 15 s timeout;
  - three retries with backoff on network errors and 5xx for **every method**, POSTs included. Sensitive writes opt out with `skipRetry`;
    avatar upload and push-token registration do not. No write sends an `Idempotency-Key`.
  - alerts for 402 and 403 entitlement answers, in English;
  - a logout on 401.
  
  Of 27 `useQuery` calls, only 4 files handle `isError`; most screens fall back to empty or zero states. Defensive `try/catch` around
  SecureStore is thorough.
- **i18n: none.** Every string is English and inline. The 402/403 alerts refer to a `lib/i18n` module that does not exist. The platform's five
  locales (en, ru, de, fr, es) are absent. `toLocaleString()` uses the device locale, and dates go through 28 bare `new Date(...)` parses with no
  venue time zone.
- **Accessibility.** There are 20 accessibility labels and 10 roles across about 311 touchables. Tab labels are labelled; most buttons and icon
  buttons are not. There is no font-scaling handling. `userInterfaceStyle: "light"` sits on a dark UI.
- **Hotel-only assumptions** (about 62 hard-coded lines):
  - Brand and copy: "Hotel Loyalty" on login, "Contact Hotel", "Hotel Services", "Your hotel is curating…", and the share text "Join me on
    Hotel Loyalty".
  - The Help FAQ talks about "every qualifying stay … front desk".
  - Home always shows the photo tiles "Book Stay", "Spa & Wellness" and "Dining & Services", with no capability check
    (`(tabs)/index.tsx:155-176`).
  - `lib/industryVocab.ts` covers hotel, beauty, medical and restaurant. `fitness`, `legal`, `real_estate`, `education`, `services` and `other`
    fall back to hotel words: a gym's members read "Book Stay", "guest" and "Room".
  - The industry is read from the user record cached at login and never refreshed.
- **Token storage and security.**
  - The Sanctum token, the user JSON and the member JSON are kept in `expo-secure-store` with default accessibility. That is acceptable.
  - Sanctum tokens never expire (`config/sanctum.php` `expiration => null`), and **sign-out never calls `DELETE /v1/auth/logout`**
    (`lib/store.ts` `logout`). The token stays valid on the server after sign-out. The staff app revokes its token.
  - Apple Wallet now uses a single-use, 2-minute link. That is good.
  - The QR code is the permanent `member_number` (`MemberController::card`), so a screenshot of it works forever.
  - The widget WebView runs JavaScript and lets every https navigation through (`WidgetWebView.tsx` `onShouldStartLoadWithRequest` returns true),
    and puts the member's name, email and phone into URL query strings.
  - Every merge to `main` goes straight to devices as an unsigned over-the-air update.
- **Dead code.**
  - 8 of the 14 exported UI components are never imported: DateField, GlassCard, GlassStatBar, PointsCounter, PremiumInput, ProgressRing,
    SegmentedPills, TierBadge.
  - `lib/queryKeys.ts` is unused.
  - `@shopify/flash-list` and `expo-system-ui` are never imported. `@react-native-community/datetimepicker` is used only by the dead DateField.
  - 130 hex colours are hard-coded outside `lib/theme.ts`, so the venue's theme does not reach them. `fontWeight` is used 139 times, often
    without an Inter face.
  - Info.plist purpose strings mention "venue check-ins" and "save receipts"; the app has neither feature.
- **Dependency age.** Everything is pinned to the SDK 54 set, four SDKs behind the staff app. `react-native-screens` 4.16 against 4.30,
  `gesture-handler` 2.28 against 3.3 (a major version), RN seven minor versions behind. `package-lock` has 809 packages.

## 4. Design

- **Members' app.** Near-black `#0d0d0d` background with `#161616`/`#1e1e1e` surfaces, gold `#c9a84c` accent, and white and `#8e8e93` text.
  This is exactly AppLook's "Gold Classic" preset (`app/Services/Loyalty/AppLook.php:52`).
  - Type: Cormorant Garamond for headings and figures, Inter for body text (`lib/theme.ts` `fonts`).
  - Main components: metallic tier cards (`components/ui/LoyaltyCard.tsx`: SVG and gradient "metals" per tier name), an animated floating tab bar
    (`AnimatedTabBar.tsx`; tabs Home, Benefits, Activity, Profile), a QR modal that raises brightness, a points chart, Lottie empty states, a gold
    SVG aura on login, `PressableScale`, haptics and skeletons.
  - The look is themable per venue at run time: `applyTheme` takes 11 colours plus card style, radius, button style and accent intensity from the
    `mobile_app` settings that the Loyalty workspace's AppLook writes, and remounts the navigator to apply them.
  - The icon, splash, adaptive icon and notification tint are sky blue `#0ea5e9`, which clashes with the gold-on-black inside the app.
- **Staff app.** Deep navy `#07090f`/`#10141d`, the same gold `#c9a84c` with a metallic `GOLD_GRADIENT`, warm text `#f7f4ee`, the same two fonts,
  one fixed dark theme, and every colour and type style taken from `src/lib/theme.ts`. Its header comment describes it as the previous apps'
  "gold on deep navy, made deeper and quieter".
- **How close they are.** Same gold and same typefaces. The differences are the charcoal base instead of navy, looser token discipline, and the
  blue store icon. A rebuild could start from the staff theme as the default and keep the venue's AppLook colours as the override, since the
  workspace already writes them.

## 5. Inputs for the decision

**What can be reused**

- **All of the server.** Every endpoint above stays, and `member/portal/*` already serves everything the app lacks.
  `routes/api.php:415-416` says the mobile endpoints keep their shapes.
- **From the portal** (`frontend/src/portal/`), as framework-free TypeScript:
  - `pages/book/steps.ts`, `payOutcome.ts`, `pages/stay/staySteps.ts`, `pages/events/eventMath.ts`, `pages/homeMath.ts`, `memberCardMath.ts`,
    `lib/money.ts`, `lib/dates.ts`, `lib/plural.ts` (needs i18next), and `lib/types.ts`;
  - the five-locale JSON bundles (`i18n/portal.*.json` plus `credit`, `events`, `help` and `stamps`; about 33 KB of English).
  
  These can only be shared if the new app lives in this repository (`apps/`, beside the staff app), with a Metro `watchFolders` set-up.
- **From the staff app:** the API client and session handling (including server sign-out), the five-locale i18n with its parity test, the
  theme tokens and UI kit, the push module, the biometric lock, the `EXPO_OFFLINE` notes and the EAS profiles.
- **From this app:** the visual ideas (metal card, QR brightness boost, Lottie states), the defensive SecureStore wrapper, the Apple Wallet
  nonce flow, the join-link and QR parser (`join.tsx`), the review screen, and the store identity.

**What would have to be rewritten under either option**

- Nearly every screen: strings need translating, and 130 colour literals need replacing.
- The data layer: move to `member/portal/*`, and read capabilities and vocabulary from the server.
- Bookings and booking detail, and booking with payment: native Stripe (`@stripe/stripe-react-native`), or a WebView of the portal's own
  booking with a member session.
- Inbox and push routing.
- Progress wording, tier colours, and Help.
- New screens for stamps, credit, events and benefit requests.
- On the server: multi-device push and token removal for members. Members currently have only `POST /v1/auth/push-token`.

**Effort.** These are rough figures for one experienced developer working with an agent.

- **Upgrade in place.** First, four SDK jumps (54 → 58) with the New Architecture forced on, RN 0.81 → 0.88, gesture-handler 3, and every
  native module checked again. Allow 1–2 weeks with a real crash risk on iOS, given the history. Then the rewrite list above, about
  4–6 weeks. In practice every screen gets touched while the legacy structure stays: no tests, `any`-typed data, and theme literals.
- **New app on the staff app's toolchain.** Set-up and shell come almost free from the staff app. About 20 screens need building against
  `member/portal/*`, using the portal's logic and words. Allow about 4–6 weeks to reach parity with the portal plus push, wallet, QR and chat.
  Payments are the largest and riskiest part. The result has tests, five languages and every industry from day one.

**Risks, and how to keep the store listings**

- **Keep the identity**, so that existing installs update instead of needing a new download:
  - bundle id `com.hotelloyalty.app` on both stores, App Store Connect app `6765608479`, team `HNWSAQ5CQ9`;
  - EAS project `865bfb65-…` under `hoteltechai`, which holds the remote build counters (iOS 17, Android 8) and the Android upload key in EAS
    credentials;
  - the scheme `hotel-loyalty://`, used by join and review links and in `DocumentationController`.
  
  The display name and the store listing can be renamed. A new id such as `uk.hexatech.loyalty.member` would be a new listing: existing
  members would not migrate and the reviews would be lost.
- **Keep members signed in.** Read the existing SecureStore keys (`auth_token`, `auth_user`, `auth_member`, `biometric_required`,
  `onboarding_seen`). With the same bundle id and team, they survive the update.
- **Over-the-air updates.**
  - Today's binaries use runtime version `1.2.0` and take updates from branch `production`. Give the new binary a new runtime version.
  - Stop or replace the push-to-`main` workflow, so that old binaries never get incompatible bundles and unreviewed code no longer reaches
    members automatically.
- **Android submission is manual.** The `google-services-key.json` file is missing on the build machine. Android push also needs an FCM V1 key in
  EAS before anything works there. Nothing would regress, because it has never worked.
- **Review and testing time.** Apple review is required for a new binary. Payments inside an app also need Apple's in-app purchase rules
  checked: real-world services and stays are normally exempt.
